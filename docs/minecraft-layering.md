# Minecraft MCP 仓库分层与抽象路线

配套依据：[总体设计](minecraft-framework.md)。本文规定目录职责、依赖方向和逐层抽象的顺序，不规定实现类、函数、工具名称或必须包含哪些动作。

目录以未来独立仓库为根，当前只固化设计，不创建空代码脚手架。目录代表责任边界，首版大部分 TypeScript 代码仍运行在同一个进程中；目录分开不意味着需要拆成服务。

## 1. 仓库组织

```text
项目根目录/
├── apps/
│   └── agent/                    # Node.js 主程序、配置装配、连接与退出
├── packages/
│   ├── contracts/                # 跨边界的公共语义和数据约定
│   ├── foundation/               # 外部能力入口及少量公共基础设施
│   ├── world/                    # 事实、空间关系、语义对象与查询
│   ├── execution/                # 局部闭环、持续监测、控制协调与验证
│   ├── tasks/                    # 子目标依赖、任务组合、进度与恢复
│   ├── knowledge/                # 可复用方法、适用范围与验证记录
│   ├── interfaces/
│   │   └── mcp/                  # 模型入口、调用转换与结果呈现
│   └── adapters/
│       ├── mineflayer/           # Mineflayer、路径插件及游戏版本差异
│       ├── telemetry/            # 服务端观测接口的客户端
│       └── vision/               # 可选画面来源
├── mods/
│   └── server-observer/          # Java/Fabric 服务端观测与标记
├── scenarios/                    # 场景定义、人工区域、示例蓝图与配置
├── tests/
│   ├── semantics/               # 条件、证据与组合含义的测试
│   ├── replay/                  # 基于录制事件的判定和恢复测试
│   └── integration/             # 真实游戏环境与端到端测试
├── tools/                        # 开发、构建、环境启动与测试辅助
└── docs/                         # 总体设计、分层、环境兼容性和设计变更
```

apps/agent 是唯一装配入口：选择后端、建立运行环境、连接 MCP 与本地执行机制。业务模块不自行创建另一套机器人连接。

mods/server-observer 是另一种语言和运行环境，但属于同一仓库，便于主程序与观测接口共同版本化。它的职责是读取服务端事实、采集事件和保存区域标注；世界语义推导与任务规划留在 Node.js。

contracts 只容纳跨边界需要一致理解的内容，不成为所有内部类型的集合。Node.js 与 Java 交界的数据约定以一份公开规范为准，各端用一致性测试核对。

foundation 提供外部观察、控制、画面和必要存储等能力的入口。只加入已被实际使用证明需要的公共基础，不预建庞大的通用插件框架。

knowledge 存放方法定义与适用信息，scenarios 存放具体场景数据；运行日志、账号信息、世界存档和训练/实验产物存放在配置的运行目录，不混入代码和可复用方法。

## 2. 逻辑层与部署层分开

| 逻辑层 | 解决什么问题 | 主要对应目录 |
|---|---|---|
| 接入层 | 怎样获取游戏事实、调用底层能力、连接画面来源 | adapters、mods |
| 基础语义层 | 不同来源的信息怎样表达，哪些能力可用 | contracts、foundation |
| 中层：世界解释 | 现在有什么、哪些关系成立、哪些条件满足 | world |
| 中层：局部执行 | 给定局部目标怎样完成、验证、监测和退出 | execution |
| 高层：任务组织 | 一个目标怎样展开、组合、重规划和恢复 | tasks、knowledge |
| 交互与装配 | 模型怎样调用，程序怎样启动和维持生命周期 | interfaces、apps |

模型负责的高层决策位于 MCP 客户端中。仓库内高层提供目标表达、可复用方法和任务执行，不重复建设一个内置模型代理。

MCP 入口不属于游戏控制的高层算法，它是对任务与观察能力的调用界面。服务端 Mod 也不因运行在服务器上就承担任务高层；它仍是事实来源。

## 3. 高层抽象到什么程度

### 3.1 目标与约束

高层表达要达到的世界状态、对象范围、允许使用的资源和方法、风险与停止条件。用户意图必须转换成可以检查的目标解释；无法形式化的部分保留模型评审位置。

高层可以说“连接这两个区域并保留指定结构”，中层负责求解局部几何与控制。高层无需持有协议包、鼠标角度或具体插件对象。

同一目标可能有多种方法。方法选择考虑代价、条件和风险；确定的边界内由程序选择，需要改变策略或任务含义时交回模型。

### 3.2 方法与组合

可复用方法说明：适用于什么条件、需要哪些中层能力、建立哪些子目标、允许何种局部修复、怎样判断整体完成。其内部可以采用顺序、条件、有界重复或依赖关系，不要求首版就提供通用规划语言。

高层组合的单位是带条件和效果的行为。方法描述语义而非某次运行的固定坐标与对象；具体场景绑定在执行准备时完成。

方法保存来源、适用环境与验证记录。候选方法和已验证方法分别管理；更新后重新验证受影响范围。语义检索可以辅助找方法，但适用条件决定方法能否调用。

### 3.3 任务进度与恢复

任务状态表达已满足的子目标、已产生效果、未解决条件和仍需决策的问题。进度不能只表示执行到列表第几项。

局部结果返回后，高层更新依赖并继续；中断或环境变化后，核对仍成立的目标再重新展开。整体完成由任务级条件确认，而非简单汇总子步骤曾经成功。

高层不承担实时运动、逐帧战斗或每次交互的重试细节；它接收中层反馈的完成、阻断、中断及不确定效果。

## 4. 中层抽象到什么程度

中层是连接目标与具体游戏 API 的主体。它有两个相互协作的部分，不能只抽象“技能列表”。

### 4.1 世界解释与可行性

世界解释统一原始事实的对象身份、来源、时间、覆盖和未知状态，再建立可站立、可达、可交互、遮挡、连通、支撑等任务相关关系。

它输出具体可行方案及条件，不直接发游戏指令。可行性结论必须能追溯到事实，事实改变时使依赖它的结论失效。结构标签关联到几何对象，并保留人工、蓝图或算法来源。

世界模型不预计算所有空间关系。高层提出任务范围，中层按需要展开局部关系，并保留精确数据供执行与验证使用。

### 4.2 局部闭环与验证

中层将一个有界局部意图转换为具体控制，负责前置检查、反馈修正、持续监测、效果验证和可解释退出。

开始条件、持续条件和完成条件分别表达。验证使用世界证据，不能由控制代码“我执行完了”的内部标记替代。初期可在同一模块实现，但逻辑上必须能够单独测试控制与判定。

中层处理可以在既定目标与约束内解决的变化。需要改变目标、方法或预算时将问题交给高层。单次输入、一个局部行为和持续任务的边界通过真实执行归纳，不根据函数长度或 API 数量划分。

### 4.3 控制协调与中断

中层统一占用移动、视角、物品和界面等控制资源，保证首版同一机器人只有一个修改执行分支。监测与只读查询可以同时运行。

退出过程属于行为语义的一部分。更换控制器前先核对在途效果并完成适用的交接；不假定统一清空输入适用于所有状态。各玩法可以复用中层的局部控制，不得在旁路自行控制角色。

### 4.4 向高层返回什么

返回当前结果、已发生效果、相关资源变化、失效条件、必要证据和可继续的边界。高层接收到的是“下一步决策需要的信息”，同时可以按需展开精确数据。

它既不返回无解释的底层异常，也不把所有细节压成一句自然语言成功。第三方错误在适配层解释，业务原因在中层表达，任务意义在高层判断。

## 5. 依赖方向与通信边界

核心依赖方向为：**任务组织依赖中层能力；中层依赖基础语义与能力入口；适配器实现这些入口；主程序把它们连接起来。**

具体规则：

- contracts 不依赖 Mineflayer、Fabric、MCP 或任何任务实现。
- world 和 execution 不导入具体后端；execution 查询 world，world 不调用控制器。
- tasks 通过 world 查询条件、通过 execution 推进行为；execution 通过结果和事件反馈任务，不反向调用高层方法。
- knowledge 定义方法及其适用信息，由 tasks 解释执行；不自行连接游戏。
- adapters 可以使用对应第三方库，通过约定能力入口提供事实和控制，不能自行加入上层目标或偷偷增加任务副作用。
- interfaces/mcp 调用任务与观察能力，完成边界参数校验和结果呈现；不另写一份执行逻辑。
- apps/agent 负责装配、运行配置和生命周期，避免业务模块各自维护同一连接或会话。

依赖倒置让中层不需要认识具体 Mineflayer 对象；不要求在第一版为每种可能后端做实现。协议数据经过适配后才进入业务层，客户端预测与服务端事实不能在适配时被无差别合并。

Mod 与主程序的共享范围止于事实、事件、区域标记和必要能力说明。不能让同一几何判断、任务计划或结果判定同时在两端各实现一套并彼此不一致。

## 6. 按什么顺序逐层抽象

抽象顺序依据可靠性和共性，不按玩法逐个建设完整子系统。下面每一阶段都规定“先证明什么”和“再固化什么”，不指定必须实现哪些类或动作。

| 阶段 | 先探索和证明 | 再固化的抽象 | 进入下一阶段的条件 |
|---|---|---|---|
| 一：接入事实 | 连接、观测、操作、回调、服务端变化的实际顺序和边界 | 外部能力入口与最小归一化数据 | 能区分已发送、预测变化、真实观察和未知 |
| 二：对象与状态 | 同一对象跨观察如何识别，时间、覆盖和缺失如何变化 | 稳定对象引用、状态来源与有效性 | 旧状态和未知状态不会被误作当前事实 |
| 三：局部闭环 | 选择少量有不同反馈特征的操作，观察正常、拒绝、超时和中断 | 通用条件、局部执行、证据和退出语义 | 能独立解释为什么开始、怎样完成、为什么停止 |
| 四：空间与对象关系 | 在多个闭环中找出重复出现的几何和条件判断 | 可行性关系、依赖失效、语义对象边界 | 关系可追溯且能随相关事实变化而失效 |
| 五：组合与恢复 | 组合局部闭环，主动改变前提并验证恢复 | 子目标依赖、预算传播、局部修复和整体判定 | 保留真实进度，修复只影响相关部分 |
| 六：方法与跨场景复用 | 在多个任务和地形中验证同一组合的适用范围 | 参数化方法、适用条件和验证记录 | 新场景主要绑定参数或替换方法，而非修改核心运行机制 |
| 七：语义与视觉扩展 | 确认哪些问题程序事实无法表达或判断 | 自动对象识别、视觉补充和模型评审边界 | 扩展结果仍能关联到对象、条件和证据，不绕开执行机制 |

阶段不是七次大重构。开始时按上述目录边界放置最小代码，每一阶段通过实践补全对应内容。局部实验需要的几何检查可以先存在于行为内部，只有在复用需要和语义都明确后，才提取到统一关系层。

### 6.1 什么时候提取共同抽象

只有多个实例共享以下含义时，才提取为同一机制：输入对象如何解释、开始和结束的含义、失败与未知如何处理、退出与副作用如何约束。

外观相似但完成含义不同的过程可以共享底层工具，不必合并成同一行为。为新增玩法不断添加互斥开关，通常说明原来的行为边界过宽。

实现中遇到一个特殊例子时，先保留局部实现和适用限制。不要立即扩大通用接口，也不要假定一个成功案例证明普遍适用。

### 6.2 什么时候允许向更高层抽象

下层的适用条件、实际效果和退出行为经过验证后，上层才能把它当稳定能力。一个操作在顺利环境中能跑通，只证明存在成功路径，不足以成为可靠组合单元。

高层抽象必须保持下层限制可见。把若干步骤包装成一个名字时，不能丢失材料限制、修改范围、风险、未知状态和中断约束。

### 6.3 什么情况下回到下层修正

出现误读时先定位责任：原始信息错误属于接入；对象或关系解释错误属于 world；局部控制或判定错误属于 execution；组合顺序或恢复错误属于 tasks；用户意图解释错误属于高层决策。

在对应层修正后重跑受影响的组合。不得在高层用更多提示词长期掩盖稳定的底层错误，也不得把任务特例塞入通用观测接口。

## 7. 与开发和验证组织对应

每层先做最小可运行纵向链路，再扩大覆盖。界面可早接以便试用，但 MCP 工具数量不驱动内部抽象；同一核心可以先通过测试脚本直接调用，再由 MCP 暴露。

验证分工：

| 验证类型 | 负责证明 | 不能代替 |
|---|---|---|
| 语义测试 | 条件逻辑、未知传播、范围约束与目标判定 | 真实游戏行为 |
| 事件回放 | 时间变化、失效传播、中断与恢复的判定 | 实际运动及第三方取消行为 |
| 真实集成 | 协议、预测、控制、服务端事件与画面来源 | 所有环境的普遍兼容 |
| 跨任务场景 | 分层是否可复用，组合是否保留约束 | 用户意图本身的澄清 |

首先固定一个版本组合记录实际行为，再扩大兼容范围。性能优化要保持语义一致，不能以减少观测为由取消所需验证。

## 8. 后续变化放在哪里

| 变化 | 优先修改的范围 |
|---|---|
| 更换 Mineflayer 版本或游戏协议差异 | 适配器与兼容性验证 |
| 增加服务端可观察信息 | Mod、观测适配和对应事实；需要时增加关系 |
| 换 Paper 观测后端 | 新观测实现，保持公共语义 |
| 增加新玩法 | 必要的中层关系/闭环与高层方法 |
| 增加更复杂建筑识别 | 世界语义推导及其来源，不改变基本控制通路 |
| 增加真实客户端画面 | 视觉适配和观测呈现 |
| 接管实际客户端角色 | 新控制适配及其能力验证；不能假定 Mineflayer 插件直接复用 |
| 替换模型或接入其他调用方式 | 外部模型或 interface，核心任务机制保持独立 |
| 需要客户端退出后持续运行 | 程序装配与进程通信，任务与闭环语义保持一致 |

只有新需求改变了目标、效果、时间、对象或证据的共同含义，才进入跨层设计变更。其余扩展在所属层完成，避免新增一个玩法就重写主框架。
