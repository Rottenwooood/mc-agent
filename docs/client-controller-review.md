# Route B(真实客户端控制)—— 现状梳理与设计问题

> 哪些不稳、以及暴露出的**设计层问题**(不是 bug)与可选改动方向。
> 日期:2026-10-10。作者:实现过程中的自我复盘。

## 1. 现状

### 1.1 实现面
- **单 Mod `mods/mcagent`**:`main` 源集 = 服务端只读观测(HTTP 8765,原样);
  `client` 源集 = 真实客户端本地玩家控制(HTTP 8766)。`splitEnvironmentSourceSets()`,
  一个 jar 两个环境。
- **客户端控制原语** ≈ `ControlPort` 全量:走/看/挖/放/用/攻击/交互/背包/容器/合成/熔炼/附魔/
  铁砧/交易/聊天/命令 + 客户端只读(raycast/配方/世界信息/可达/可见)+ `respawn`。
- **TS 适配器 `@mc-agent/adapters-client-mod`**:`ClientModControlPort implements ControlPort`;
  `MCAGENT_CONTROL=client-mod` 选择后端。`apps/agent` 装配处 `ctrl` 类型放宽为 `ControlPort`。
- **启动器**:`tools/launch-client.mjs`(从 launcher 版本清单直接起客户端,离线鉴权,
  `--quickPlayMultiplayer` 自动入服)、`tools/client-up.sh`(构建+安装+启动)、
  `tools/fetch-fabric-api.mjs`。
- **上层零改动**:执行引擎 / L1 reflex / L3 契约 / 工具面(49)/ 二级动作 / skill / 感知。

### 1.2 已验证能用
- 启动 → 入服 → `/health`;经 resident 用 mc-agent 工具驱动。
- 走位(**不破坏**):短/中距离到达、**绕路(破坏 0 块)**、不蹦。
- 单块挖/放(`set_block`,**服务端事件权威确认** `actor=Agent`);`go_to`/`set_block` 返回 `pass`。
- 合成链:木板 → 木棍 → 工作台 → 木镐(全部 `pass` + 背包增量)。
- **正确工作流**:`scan_blocks` → `go_to` 到大致位置 →
  `run_method(for_each members(handle) → set_block(air))` 挖一棵树(7 成员 4 成 3 败,
  **返回每步判定** + 拿到原木)。

### 1.3 不稳 / 坏
- **挖穿到远处地下目标**:慢、易卡、曾把角色**带进岩浆烧死**(现由守卫拦下,但会中断任务)。
- **危险检测**只在 walker 里 ad hoc 判,没有统一定义。
- **证据分级错**:中途破坏的方块是**客户端自报**,却被当权威证据用。
- **对象→格**解析靠启发式(`resolveObject` 取"最近暴露格")。

## 2. 暴露出的设计问题(根因,不是 bug)

1. **客户端控制层自己扛了最难的两件事:导航 + 挖穿。**
   mineflayer 后端用的是成熟库 `mineflayer-pathfinder`(含 `canDig`);手写的 A*+Digger 在
   "3D 挖穿到远处地下目标"上**先天不足**:搜索空间爆炸、执行风险(岩浆/坠落)、易卡。
   **这是选型问题,补丁解决不了。**

2. **"挖掘"与"到达/导航"职责混淆。**
   一个"挖一个方块"的 `set_block`,因为 `navigate` 会去隧道、`Digger` 会破坏挡路块,实际顺带做了
   大量导航+破坏。语义不清、进展难断言、危险难控。

3. **证据分级。** 客户端自报 ≠ 权威。进展证据应标 `observed`,只有服务端 observer 事件确认后
   才能升 `authoritative`。

4. **对象→格交给单个动作猜。** 一个矿脉/树"挖哪些格、按什么顺序"应由**组合**
   (`members`/`for_each`)表达,而不是让单个动作猜一个"最近暴露格"。

5. **安全不变量没有统一定义/分层。** reflex 只看敌对/弹射物/血量;地形危险(岩浆/火/坠落)在
   walker 里另写一套。应有**统一的安全不变量**(危险集合 + 检测层)。

6. **缺少受限、可复现的测试场景。** 一直在真实复杂地形上碰运气;应在平地/固定种子上先验证
   走位/挖掘/合成,再上真实地形。

## 3. 设计层可选的改动方向(待拍板)

### A. 客户端控制层的分工
- **A1(倾向)**:客户端 Mod 只做"玩家合法原语 + **不破坏**走位";**"挖穿到达"用组合显式表达**
  (挖阶梯/竖井:`run_method` 对沿线的 `area`/`box_cells` 格 `set_block(air)`)。
  → 安全、可断言、符合有界词表;代价:组合要会写"挖阶梯"。
- **A2**:客户端引入成熟寻路(如 Baritone)。→ 一劳永逸;代价:重依赖,且不再是"自己的控制层"。
- **A3**:继续打磨自研隧道 A*。→ 最难、风险最高,不建议。

### B. 语义拆分
把 `ControlPort`/动作拆成 **到达(reach)** 与 **作用(act)** 两件事;`set_block` 不再隐式隧道。

### C. 证据分级
客户端自报进展标 `observed`;observer 事件确认后升 `authoritative`。

### D. 安全
定义统一的安全不变量(危险集合/检测层),明确放进 **L1 reflex** 还是 **walker 契约**。

### E. 测试
先做**受限场景**(平地/固定种子)验证走位/挖掘/合成,再上真实地形;把"演示"从"真实复杂地形
碰运气"改成"受限场景确定性通过"。
